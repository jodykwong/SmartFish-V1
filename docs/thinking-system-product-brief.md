## 1. Vision (愿景)

### 1.1 产品愿景
将 SmartFish 从"舆情分析工具"升级为"思考-决策-执行完整闭环系统"，帮助创业者和产品负责人避免在错误方向上高效执行，通过强约束筛选和自动化工件生成，实现从想法到落地的无缝转化。

### 1.2 核心价值主张
**"不让你高效地把错误方向做完整"**

- 用决策宪法Gate阻止高风险想法进入执行
- 用BMAD路由自动生成可落地工件
- 用AI Agent补强证据链
- 用Zero to Sold方法论验证市场

### 1.3 成功指标
- 用户每周至少记录3条思考
- Gate否决率: 30-40% (证明有效筛选)
- 通过Gate的条目中，80%生成工件
- 用户决策后悔率降低50%

## 3. Problem Statement (问题陈述)

### 3.1 核心问题
**"想法很多，但90%都是错的，而且很难提前知道哪个是对的"**

### 3.2 现状分析

**用户当前的解决方案**:
- 用Notion/Excel记录想法 → 缺少筛选机制
- 凭直觉做决策 → 受情绪和认知偏差影响
- 手动写PRD/Tech Spec → 耗时且容易遗漏
- 零散地做市场调研 → 缺少方法论指导

**痛点强度评分**: 8/10 (重要且紧急)
- 重要性: 错误决策成本极高
- 紧迫性: 创业窗口期有限
- 频率: 每周都会遇到

### 3.3 问题验证证据
- SmartFish现有用户反馈: "分析很好，但不知道接下来做什么"
- 创业失败统计: 70%失败于方向错误而非执行问题
- 用户访谈: "我需要一个能说'不'的系统"

---

## 4. Solution Overview (解决方案概述)

### 4.1 核心解决方案

**四大支柱**:

#### 支柱1: 决策宪法Gate (强筛选)
- 四层过滤器: 人性依赖/价值自证/反馈清洁度/角色消耗
- 否决式设计: 任一层不通过即终止
- 审计追踪: 所有决策可回溯

#### 支柱2: BMAD工作流路由 (自动化)
- Quick/Standard/Enterprise三档
- 自动生成工件: tech-spec/PRD/architecture
- 模板可配置

#### 支柱3: AI证据补强 (智能化)
- 调用QueryEngine/MindSpider/InsightEngine
- 自动采集市场声音
- 回填证据链

#### 支柱4: Zero to Sold方法论 (系统化)
- Audience → Problem → Solution → Product
- 访谈脚本生成
- 市场转向复核

### 4.2 差异化优势

| 维度 | 竞品 | SmartFish ThinkingGate |
|-----|------|----------------------|
| 筛选机制 | ❌ 无 | ✅ 强Gate |
| 工作流 | ⚠️ 手动 | ✅ 自动路由 |
| 证据补强 | ❌ 无 | ✅ AI Agent |
| 方法论 | ⚠️ 零散 | ✅ 内置 |
| 闭环 | ❌ 断层 | ✅ 完整 |

### 4.3 MVP范围 (Phase 1)

**必须有**:
- Gate四层过滤
- 基础思考条目CRUD
- Quick路由 + tech-spec生成
- 简单UI

**不包含**:
- Agent集成 (Phase 3)
- Zero to Sold完整向导 (Phase 4)
- 高级分析面板 (Phase 4)

## 5. User Journeys (用户旅程)

### 5.1 核心旅程: 每日思考

**场景**: Alex早上喝咖啡时想到一个新产品idea

```
1. 打开SmartFish → 点击"新思考"
2. 填写Signal: "看到朋友抱怨找不到好的XX工具"
3. 进入Gate检查:
   Q1: 这个依赖用户持续主动使用吗? → 是 → ⚠️ 警告
   Q2: 需要反复向用户解释价值吗? → 否 → ✅ 通过
   Q3: 用户反馈是否可量化? → 是 → ✅ 通过
   Q4: 你需要推动事情发生吗? → 是 → ⚠️ 警告
4. Gate结果: 通过但有2个警告
5. 填写结构化字段:
   - Target: 独立开发者
   - Problem: 现有工具太复杂
   - Hypothesis: 简化版能获得10%市场
   - MVA: 48小时内做原型
6. 系统建议: Quick路由
7. 生成tech-spec.md
8. 标记"本周执行"
```

**时间**: 10-15分钟
**结果**: 1个可执行的tech-spec + 清晰的风险认知

### 5.2 次要旅程: 证据补强

**场景**: Sarah需要验证一个假设

```
1. 打开已有条目
2. 点击"补强证据"
3. 输入研究问题: "用户真的觉得现有工具复杂吗?"
4. 选择QueryEngine
5. 系统生成搜索任务
6. 等待5-10分钟
7. 查看证据摘要:
   - 找到15条相关讨论
   - 8条提到"太复杂"
   - 3条提到"学习成本高"
8. 一键回填到条目
9. 更新假设置信度: 60% → 75%
```

**时间**: 30-40分钟
**结果**: 假设得到验证，置信度提升

### 5.3 周度旅程: 评审与规划

**场景**: David周日晚上回顾本周思考

```
1. 进入"周度评审"
2. 看到本周7条思考:
   - 3条通过Gate
   - 2条被否决
   - 2条待完成
3. 对通过的3条打分:
   - 影响力: 8, 7, 6
   - 可行性: 7, 9, 8
   - 证据: 6, 8, 7
4. 选择Top 2进入"本周计划"
5. 生成weekly-plan.md
6. 设置提醒
```

**时间**: 30-60分钟
**结果**: 清晰的本周执行计划

## 6. Key Features (关键功能)

### 6.1 功能优先级

#### P0 (MVP必须有)
- F1: 思考条目CRUD
- F2: Gate四层过滤
- F3: Quick路由 + tech-spec生成

#### P1 (Phase 2)
- F5: Standard/Enterprise路由
- F6: 工件模板系统
- F7: 周度评审
- F8: 导出功能

#### P2 (Phase 3)
- F9: QueryEngine集成
- F10: 证据回填
- F11: 任务调度

#### P3 (Phase 4)
- F12: Zero to Sold向导
- F13: 市场声音采集
- F14: 市场转向复核

### 6.2 功能详细说明

#### F2: Gate四层过滤 (核心差异化)

**输入**: 思考条目基本信息
**处理**:
1. 人性依赖检查: 是否强依赖他人意愿/持续动力?
2. 价值自证检查: 是否需要反复解释价值?
3. 反馈清洁度检查: 反馈是否可量化/可证伪?
4. 角色消耗检查: 是否需要你推动事情发生?

**输出**:
- 通过: 进入下一步
- 否决: 标记层级+原因，锁定后续流程
- 警告: 通过但标记风险

**验收标准**:
- 任一层否决后，无法生成工件
- 否决原因必须填写
- 审计记录不可篡改

#### F3: Quick路由 + tech-spec生成

**触发条件**: Gate通过 + 用户选择Quick
**生成内容**:
```markdown
# Tech Spec: [标题]

## 目标
[从条目自动填充]

## 范围
- In Scope: [MVA]
- Out of Scope: [约束]

## 验收标准
[Success Metric]

## 风险与止损
[Gate警告 + 依赖]

## 时间表
- 开始: [今天]
- 完成: [48小时后]
```

**验收标准**:
- 文件自动命名: YYYY-MM-DD_slug_tech-spec.md
- 保存到docs/thinking/
- 可手动编辑

## 7. Success Metrics (成功指标)

### 7.1 北极星指标
**"每周生成的可执行工件数"**

目标: 
- Phase 1: 5个/周 (单用户)
- Phase 2: 20个/周 (10用户)
- Phase 3: 100个/周 (50用户)

### 7.2 关键指标

#### 使用指标
- 每周活跃用户 (WAU)
- 每用户每周思考条目数
- Gate通过率 (目标: 60-70%)
- 工件生成率 (目标: 80%+)

#### 质量指标
- 用户决策后悔率 (目标: <20%)
- 工件被实际执行率 (目标: >60%)
- 用户满意度 (NPS目标: >40)

#### 效率指标
- 从想法到工件的平均时间 (目标: <20分钟)
- Gate完成时间 (目标: <5分钟)
- 证据补强时间 (目标: <30分钟)

### 7.3 反向指标 (需要监控)
- Gate否决率过高 (>50%): 可能过严
- 工件生成后不执行率 (>50%): 可能质量不足
- 用户流失率 (>30%/月): 可能学习成本过高

## 8. Technical Considerations (技术考量)

### 8.1 架构原则
- 模块化: Gate/路由/工件生成独立
- 可扩展: 新路由类型/工件模板易添加
- 可测试: 核心逻辑有单元测试
- 可观测: 关键流程有日志和监控

### 8.2 技术栈
- 后端: Flask + Blueprint
- 数据库: PostgreSQL/MySQL (复用现有)
- 模板: Jinja2
- 前端: 现有技术栈 (HTML/CSS/JS)

### 8.3 集成点
- 与现有Agent系统: 通过统一接口调用
- 与BMAD工件: 复用模板格式
- 与SmartFish UI: 新增入口和页面

### 8.4 性能要求
- Gate检查: <2秒
- 工件生成: <5秒
- 列表加载: <1秒 (1000条目)
- 证据补强: <60秒 (异步)

## 9. Risks & Mitigation (风险与缓解)

### 9.1 产品风险

#### R1: Gate过严导致用户放弃
**概率**: 中 | **影响**: 高
**缓解**:
- 提供"学习模式"(仅警告)
- 详细的否决说明
- 示例和最佳实践
- 可配置严格度

#### R2: 学习成本过高
**概率**: 中 | **影响**: 中
**缓解**:
- 渐进式引导
- 交互式教程
- 默认值和建议
- 视频演示

### 9.2 技术风险

#### R3: Agent集成不稳定
**概率**: 中 | **影响**: 高
**缓解**:
- 完善错误处理
- 降级方案(手动)
- 重试机制
- 独立任务队列

#### R4: 路由准确性不足
**概率**: 高 | **影响**: 中
**缓解**:
- 可解释规则
- 人工覆盖
- 持续优化
- 用户反馈

### 9.3 业务风险

#### R5: 用户规模不达预期
**概率**: 中 | **影响**: 中
**缓解**:
- 早期用户访谈
- Beta测试
- 快速迭代
- 社区建设
