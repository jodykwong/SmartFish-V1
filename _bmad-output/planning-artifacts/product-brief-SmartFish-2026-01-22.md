# Product Brief: SmartFish 思考决策系统

## Executive Summary

SmartFish 思考决策系统是一个创新的"思考-决策-执行"完整闭环系统，旨在帮助创业者和产品负责人避免在错误方向上高效执行。通过引入决策宪法Gate机制、BMAD工作流路由、AI证据补强和Zero to Sold方法论，系统将用户的商业想法转化为经过验证的可执行工件，实现从"想法"到"落地"的无缝转化。

核心价值主张：**"不让你高效地把错误方向做完整"**

---

## Core Vision

### Problem Statement

用户面临的核心问题是：**想法很多，但90%都是错的，而且很难提前知道哪个是对的。**

具体表现为两个关键断点：
1. **缺少强约束筛选**：想法进入分析或开发前没有系统化的筛选机制，导致投入在高不确定、强人性依赖或不可证伪的方向上
2. **思考无法落地**：思考很难沉淀为可执行的交付物（需求、拆解、Story、验证清单），从"想法"到"落地"存在断层

### Problem Impact

**对个人创业者的影响：**
- 时间和资源浪费在错误方向上
- 创业窗口期有限，试错成本极高
- 缺少系统化方法导致重复犯错

**对产品经理的影响：**
- 需求太多，优先级难以决策
- 决策过程不可追溯，难以复盘
- 团队执行力被错误方向消耗

**对研究人员的影响：**
- 缺少严格的验证工具和方法论
- 证据链不完整，结论可信度低
- 研究成果难以转化为实践

**问题强度评分：8/10** (重要且紧急)
- 重要性：错误决策成本极高，可能导致项目失败
- 紧迫性：创业窗口期有限，每个决策都关键
- 频率：每周都会遇到需要决策的场景

### Why Existing Solutions Fall Short

**现有解决方案的局限：**

| 工具 | 优势 | 不足 |
|-----|------|------|
| Notion/Excel | 灵活记录 | ❌ 无筛选机制，无法说"不" |
| Obsidian | 知识图谱 | ❌ 缺少工作流路由和执行转化 |
| Linear | 项目管理 | ❌ 缺少思考框架和决策支持 |
| BMAD CLI | 开发工作流 | ❌ 独立工具，无集成，无AI辅助 |
| 手动PRD | 结构化 | ❌ 耗时，容易遗漏，无验证 |

**核心缺失：**
- 没有工具能在想法阶段就说"不"
- 没有工具能自动生成可落地工件
- 没有工具能AI辅助证据补强
- 没有工具内置验证方法论

### Proposed Solution

**SmartFish 思考决策系统通过四大支柱解决问题：**

#### 支柱1: 决策宪法Gate (强筛选)
- **四层过滤器**：人性依赖/价值自证/反馈清洁度/角色消耗
- **否决式设计**：任一层不通过即终止，避免错误投入
- **审计追踪**：所有决策可回溯，支持复盘学习

#### 支柱2: BMAD工作流路由 (自动化)
- **智能路由**：Quick/Standard/Enterprise三档自动选择
- **工件生成**：自动生成tech-spec/PRD/architecture等可执行文档
- **模板可配置**：适应不同团队和项目需求

#### 支柱3: AI证据补强 (智能化)
- **多Agent集成**：调用QueryEngine/MindSpider/InsightEngine/ReportEngine
- **市场声音采集**：自动抓取tribe/water cooler的真实反馈
- **证据链回填**：验证结果自动关联到条目和工件

#### 支柱4: Zero to Sold方法论 (系统化)
- **Audience → Problem → Solution → Product**：强制正确顺序
- **访谈脚本生成**：避免偏差，聚焦真实痛点
- **市场转向复核**：持续监测市场信号，及时调整

### Key Differentiators

**竞争优势：**

1. **唯一能说"不"的系统**
   - Gate机制提供强约束筛选
   - 避免"高效地做错事"
   - 30-40%的想法会被否决（证明有效）

2. **完整的思考-决策-执行闭环**
   - 从想法记录到工件生成一站式
   - 无缝集成现有SmartFish Agent
   - 平均20分钟从想法到可执行工件

3. **AI辅助的证据补强**
   - 自动调用4个Agent验证假设
   - 市场声音自动采集和聚类
   - 证据链完整可追溯

4. **内置验证方法论**
   - Zero to Sold方法论产品化
   - 访谈脚本自动生成
   - 偏差检测和终止条件内置

5. **为SmartFish用户量身定制**
   - 复用现有舆情分析能力
   - 从"观察"升级到"决策+执行"
   - 数据和工作流无缝衔接

**时机优势：**
- AI能力成熟，可实现智能辅助
- 创业环境竞争激烈，决策质量成为关键
- SmartFish已有用户基础和Agent能力

### User Journey

#### 核心旅程：Alex的每日思考（10-20分钟）

**场景：** 周一早上，Alex喝咖啡时想到一个新产品idea

**步骤：**

1. **发现触发（0分钟）**
   - 看到朋友抱怨找不到好的XX工具
   - 打开SmartFish，点击"新思考"

2. **Gate检查（5分钟）**
   - Q1: 这个依赖用户持续主动使用吗? → 是 → ⚠️ 警告
   - Q2: 需要反复向用户解释价值吗? → 否 → ✅ 通过
   - Q3: 用户反馈是否可量化? → 是 → ✅ 通过
   - Q4: 你需要推动事情发生吗? → 是 → ⚠️ 警告
   - **结果：** 通过但有2个警告，Alex意识到风险

3. **结构化思考（8分钟）**
   - 填写Signal、Target、Problem、Hypothesis
   - 系统建议Quick路由
   - 定义MVA：48小时内做原型

4. **工件生成（10分钟）**
   - 一键生成tech-spec.md
   - 包含目标、范围、验收标准、风险
   - 标记"本周执行"

5. **成功时刻（15分钟）**
   - Alex看到清晰的执行计划
   - 风险已被明确标注
   - 知道接下来48小时要做什么
   - **"这比我自己想3天还清楚！"**

6. **长期价值（持续）**
   - 周日复盘：7条思考，3条通过Gate
   - 被否决的4条避免了至少2周浪费
   - 通过的3条都有清晰执行计划

---

**场景：** Sarah需要向VP证明一个功能值得做

7. 一键回填到PRD的"证据与洞察"章节
8. 向VP展示：有数据支撑的决策
9. **"这次VP没有质疑我的判断！"**

   - 问题强度评分：8/10
   - 典型引用和来源
   - 偏差分析和反证
8. 回填到product-brief
9. **"这个证据链可以直接用在论文里！"**

- Phase 1 (Private Beta): 5个工件/周（单用户）
- Phase 2 (Public Beta): 20个工件/周（10用户）

### User Success Metrics

#### 使用指标

**每周活跃用户（WAU）：**
- Phase 1: 10-20用户
- Phase 2: 50-100用户
- Phase 3: 200-500用户
- Phase 4: 1000+用户

**每用户每周思考条目数：**
- 目标：3-5条
- 最小：2条（保持活跃）
- 理想：5-7条（深度使用）

**Gate通过率：**
- 目标：60-70%
- 说明：30-40%的否决率证明Gate有效筛选
- 过高（>80%）：可能过于宽松
- 过低（<50%）：可能过于严格

**工件生成率：**
- 目标：>80%
- 说明：通过Gate的条目中，80%以上应生成工件
- 低于70%：说明路由或模板有问题

#### 质量指标

**用户决策后悔率：**
- 当前基线：60%（凭直觉决策）
- Phase 1目标：<40%
- Phase 2目标：<30%
- Phase 3目标：<20%

**工件被实际执行率：**
- 目标：>60%
- 说明：生成的工件中，60%以上应被实际执行
- 低于50%：说明工件质量或可行性有问题

**用户满意度（NPS）：**
- Phase 1目标：>30（种子用户）
- Phase 2目标：>40（早期采用者）
- Phase 3目标：>50（主流用户）

#### 效率指标

**从想法到工件的平均时间：**
- 当前基线：3天（手动写PRD）
- Phase 1目标：<30分钟
- Phase 2目标：<20分钟
- Phase 3目标：<15分钟

**Gate完成时间：**
- 目标：<5分钟
- 说明：四层过滤应快速完成
- 超过10分钟：说明交互设计有问题

**证据补强时间：**
- 目标：<60分钟（异步）
- 说明：从发起到结果可用
- 超过2小时：说明Agent性能有问题

## MVP Scope & Roadmap

### MVP Definition (Phase 1: 4-6周)

**核心原则：** 最小可用版本，验证Gate机制的核心价值

#### 必须有的功能（P0）

**F1: 思考条目管理**
- 创建/编辑/归档思考条目
- 核心字段：
  - Signal（信号/触发）
  - Target/Segment（目标用户）
  - Problem/JTBD（问题/任务）
  - Hypothesis（可证伪假设）
  - Evidence Needed（证据需求）
  - MVA（48小时最小行动）
  - Success Metric（成功指标）
  - Constraints/Dependencies（约束/依赖）
- 状态管理：想法/评估中/已否决/已落地/已归档
- 基础检索：按日期、状态筛选

**F2: 决策宪法Gate机制**
- 四层过滤器：
  1. 人性依赖过滤器：是否强依赖他人意愿/行动/情绪/持续动力？
  2. 价值自证过滤器：是否需要反复解释/教育市场？
  3. 反馈清洁度过滤器：反馈是否可量化/可证伪？
  4. 角色消耗过滤器：是否需要你推动事情发生？
- 否决式设计：任一层不通过即终止
- 审计记录：不可篡改的决策历史
- 否决原因：必须填写触发层级+一句话原因

**F3: Quick路由 + tech-spec生成**
- 手动选择Quick路由
- 自动生成tech-spec.md：
  - 目标（从条目自动填充）
  - 范围（In Scope / Out of Scope）
  - 验收标准（Success Metric）
  - 风险与止损（Gate警告 + 约束）
  - 时间表（48小时）
- 文件命名：YYYY-MM-DD_slug_tech-spec.md
- 保存位置：docs/thinking/

**F4: 基础UI**
- 思考列表页：显示所有条目，支持筛选
- 条目详情/编辑页：结构化表单
- Gate表单页：逐层提问，否决即止
- 简单导航：主页 → 新思考 → Gate → 工件

#### MVP验收标准

**Phase 1成功标准：**
- ✅ 用户可以创建思考条目并完成Gate检查
- ✅ Gate任一层否决后，无法生成工件
- ✅ Gate通过后，可一键生成tech-spec.md
- ✅ 至少5个种子用户每周使用
- ✅ Gate否决率在30-40%之间
- ✅ 用户反馈Gate机制"有价值"

### Scope Management

**如何防止范围蔓延？**

#### 决策原则

**加入新功能的标准：**
1. 是否直接支持核心价值主张？
2. 是否有明确的用户需求证据？
3. 是否在当前Phase的能力范围内？
4. 是否会影响已有功能的稳定性？

**说"不"的场景：**
- 功能与核心价值主张无关
- 仅有1-2个用户提出的需求
- 技术复杂度过高，风险大
- 可以通过现有功能组合实现

#### 变更流程

**如果需要调整范围：**
1. 评估对时间表和资源的影响
2. 与关键利益相关者讨论
3. 更新Product Brief和时间表
4. 记录变更原因和决策依据
